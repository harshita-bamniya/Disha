# Employer Profile UX Audit

Source: employer-portal audit (2026-09-19), triggered by a bug list (`Bugs and Suggestion.docx`) plus a request to critically review the employer flow — power distribution between company owner and departments, main-page analytics, department-scoped job posting, team invites, calendar — the way a Staff/Principal engineer would, benchmarked against LinkedIn Recruiter / Naukri RMS / Google Calendar. Findings are grounded in file:line evidence and, where possible, live browser reproduction against a real Postgres — not assumptions.

Same format as `ENTERPRISE_AUDIT_ROADMAP.md`: **Status** is `todo` / `in-progress` / `done`. Everything in the first table shipped and was tested (backend: pytest + real DB; frontend: eslint + a real project-wide `tsc` check via a scratch config, since `tsc -b` is broken project-wide on `TS5101` — see note at the bottom; UI: live click-through in the browser pane against a fresh throwaway employer account, cleaned up after).

### Known data quirk (not a bug, just a trap for next time)

The five oldest seeded employer test accounts (`employer1@beginablai.test` … `employer5@beginablai.test`) all have `company_id = NULL` — they predate the `Company`/`CompanyDepartment` model entirely. Any of E4–E9 above will 404/misbehave for those specific accounts (`_get_company_or_404` has nothing to find). Use a freshly-registered employer account for any manual testing that touches Company Profile, Departments, Team, or the paywall-exemption paths — registering through the real UI is what every verification pass in this doc actually did, and it's the only way to get a `company_id` at all right now.
