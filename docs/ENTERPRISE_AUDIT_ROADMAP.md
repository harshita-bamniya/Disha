# Enterprise Readiness Roadmap

Source: full-platform audit (2026-06-30) against LinkedIn Recruiter / Greenhouse / Lever / Ashby. Findings are grounded in file:line evidence from the codebase, not assumptions. This doc is the build backlog derived from that audit — update status as items land.

## How to read this

- **Status**: `todo` / `in-progress` / `done`
- **Difficulty**: Low (days) / Medium (1-2 weeks) / High (multi-week, needs design input)
- Items are ordered by priority within each tier. Do not skip Critical items for Medium ones without a reason recorded here.

## M2 — resolved; M5 — why it's still `todo`

Everything else Critical/High/Medium has shipped (see build log). M5 is deliberately still open — it needs something this session structurally cannot provide: a third-party credential/contract, not just more engineering time. Building it now would mean faking the missing piece, which is worse than leaving it `todo` with a clear trigger condition.

### M2 — Offer letter generation + e-signature (done, 2026-07-03)

**Correction to this doc's original framing:** offer-letter PDF generation (`app/modules/matching/offer_pdf.py`, reportlab-based) already existed in the codebase by the time this roadmap was written — the line above claiming "no PDF generation for it... anywhere in the codebase" was wrong; it was generated ad-hoc via `POST .../offer-letter` but never persisted, which is what actually blocked e-signature (there was no record to attach a response to).

**What shipped:** option (b) from this doc's own framework — a self-built "click to accept + IP/timestamp audit log" flow, not a third-party-integrated one. New `offer_letters` table (migration `f4a5b6c7d8e9`) persists one offer per application with full status (`sent`/`accepted`/`declined`). `POST .../offer-letter` now creates/updates that record, emails the candidate a real PDF attachment (required extending `app.core.email`'s attachment support, which only handled text/ICS content — added binary/PDF attachment support via `MIMEApplication`), and notifies them in-app. The candidate can accept (types their full legal name as signature + a "read and agree" checkbox; server captures IP and user-agent) or decline (optional reason) from `MyApplicationsPage.tsx`; acceptance auto-transitions the application to `hired`, decline to `rejected`. The PDF itself now renders the signature block for real once signed (name + timestamp + IP) instead of a blank line. Employer side (`CandidatePipelinePage.tsx`) shows live status (awaiting/accepted/declined) and can download the PDF at any point.

**What's still open (not done here, and not silently claimed as done):** this is *not* a legally-binding e-signature — that still needs a third-party provider (DocuSign, Adobe Sign, SignWell, Dropbox Sign) with a paid API contract, per this doc's own original reasoning. Trigger for picking that up unchanged: when sales/product reports losing or stalling a deal specifically because self-serve acceptance isn't legally sufficient for a given jurisdiction/customer — verify with counsel before relying on the current flow for real enterprise contracts.

### M5 — API/integrations (Slack, Zapier, SSO)

**What's missing today:** No API key management UI, no webhook system, no OAuth client registration for SSO, no Slack/Zapier app. Confirmed zero infrastructure for any of this — it's not partially built anywhere in the codebase.

**What it actually requires, broken into 3 independent pieces** (don't build them as one project — they have nothing in common):
1. **SSO (SAML/OIDC)** — needs a decision on which protocol to support first (SAML is what most enterprise IT departments ask for; OIDC is simpler to implement). Needs a library (`python3-saml` or similar) and, critically, *a real enterprise customer's IdP to test against* — SSO bugs are almost always integration-specific and can't be fully shaken out against a mock IdP.
2. **Slack** — needs a registered Slack app (developer account, OAuth scopes, a public HTTPS redirect URL — i.e. this needs to be tested against a deployed environment, not just local dev) before any code is worth writing.
3. **Zapier** — needs either a public webhook/API surface for Zapier's generic webhook trigger (lower effort — could reuse the existing audit-log/notification event stream) or a registered Zapier app (higher effort, requires Zapier's developer review process).

**When to build it:**
- **Zapier-via-generic-webhooks is the cheapest entry point and doesn't require waiting on anyone** — if this is picked up next, start there: expose a `POST` webhook subscription on key events (new application, interview scheduled — the same events already wired to `notify_company_team()` in M7) that any external tool (Zapier, Make, n8n) can consume generically. This needs no third-party approval.
- **Slack and SSO should wait for a named customer ask.** Building either speculatively risks guessing wrong about which OAuth scopes / SAML attributes a real enterprise buyer actually needs. Trigger: a prospect or existing customer explicitly asks for Slack notifications or SSO during a sales conversation — get their specific requirement (which IdP for SSO; what events for Slack) before writing code, not after.
- Do not bundle these three under one "integrations" ticket — they have independent triggers and shouldn't block each other.

## Explicitly out of scope for this roadmap (needs separate investigation, not assumed)

- Performance/load testing — not measured in the audit; needs the app running under representative data volume.
- Accessibility (WCAG) audit — not measured; needs a dedicated a11y pass with assistive tech.
- Full visual/UI polish pass — only one structural issue (L4) was found by reading code; a real visual audit needs the app running and clicked through.
