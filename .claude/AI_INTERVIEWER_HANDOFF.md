## Adversarial re-audit (2026-08-24, later session) — 7 real bugs found and fixed

After all 7 phases were declared done, the user asked directly: "is it actually better?" Rather than re-grading my own work, I spawned two independent agents with no stake in the prior session's claims — one doing an adversarial code review (reading the actual diff, tracing edge cases by hand), one doing hands-on live QA against the running stack (creating real sessions, trying to break things, measuring failure rates). Both were told explicitly to treat the handoff doc as an unverified claim, not a fact. **Do this again before trusting any "verified live" note in this file** — "I tried it and it worked" only proves the happy path works, and every bug below is a case where a specific edge case (not the happy path) was never actually exercised.

Current alembic head after this section: `v9w0x1y2z3a4`. Three new migrations:
- `t7u8v9w0x1y2_notification_outcome_request_type.py`
- `u8v9w0x1y2z3_session_response_is_followup.py`
- `v9w0x1y2z3a4_add_system_design_question_type.py`

**1. [Fixed] Job Readiness Report failure rate was 83% (5/6) in live testing**, from two compounding causes: Groq rate-limiting, and `generate_job_readiness_report()` in `dynamic_interview_engine.py` being the *one* LLM call site missing `reasoning_effort="low"` — on gpt-oss reasoning models, reasoning tokens draw from the same `max_tokens` budget as the actual JSON content, and this call has the largest schema of any call site (skill_scores per competency + a 4-6 entry roadmap + several string lists), so it was uniquely exposed to truncation. Fixed: added `reasoning_effort="low"`, bumped `max_tokens` 2000→3000, added a retry-once (mirroring the existing pattern in `feedback_ai.py`'s per-answer scoring). **Result after fix, measured live: zero JSON-truncation failures across 8 fresh full sessions** (previously the dominant failure mode) — the only failures remaining were genuine Groq quota exhaustion (see caveat below), which no amount of retrying can fix.
   - **Also fixed, but inert in this dev environment**: `FallbackProvider` in `ai/providers/__init__.py` only ever caught `httpx.HTTPStatusError` ≥500 — Groq's rate-limit path raises its own `RateLimitedError` (a plain `RuntimeError`, by design, for a clean message), which the fallback never saw. Now `_should_fallback()` also catches `RateLimitedError`. **Caveat found while verifying this**: `ANTHROPIC_API_KEY` is set as an env var name in this container but its value is empty (`docker exec disha_backend env | grep -i anthropic` → `ANTHROPIC_API_KEY=`), so `create_provider()` never actually wraps Groq in a fallback here — this fix is correct, real code that will matter the moment a real key is configured (e.g. in production), but don't expect it to reduce the failure rate in *this* dev sandbox until one is added.
   - **Frontend was also silently making this worse**: `JobReadinessReport` (schemas.py) never exposed the internal `error: true` flag that `_default_readiness_report()` already sets — so a degraded report was indistinguishable from a real one to any API consumer. `InterviewReportPage.tsx` rendered "0% readiness / No Hire / report generation failed" as if it were the candidate's actual final assessment. Fixed: added `error: bool = False` to the schema/TS type, `hasReport` now excludes errored reports (falls through to the honest per-answer-average hero, which was already built for non-role-specific sessions), and the report tab shows a distinct red error state ("This is a technical failure, not your actual score") with a retry CTA instead of the generic "not available for this session type" copy. **Verified live in-browser** on a real errored session — see screenshot-equivalent in that session's own testing notes.

**2. [Fixed] The predictive-validity flywheel's actual trigger has never worked.** `send_interview_outcome_requests` (the daily Celery task) calls `create_notification(..., type="interview_outcome_request", ...)`, but that value was never added to `Notification`'s `ck_notification_type` CHECK constraint — every insert violated it, the task's broad `except`/rollback swallowed the error silently, and it's been failing every single day since it was written. Only the candidate-initiated `POST /interview/sessions/{id}/outcome` path was ever tested; the automated scanner was not. Fixed: added `"interview_outcome_request"` to `NOTIFICATION_TYPES` in `models/mvp3.py` + migration. **Verified live**: backdated a real completed session's `completed_at` to 20 days ago, ran `send_interview_outcome_requests()` directly, confirmed a real notification row landed and `outcome_requested_at` got stamped; ran it again and confirmed it doesn't double-send.

**3. [Fixed] `update_skill_competence()` in `roadmap/service.py` crashed on every single interview completion for any brand-new skill** — `rec.attempts` (and the two score-avg columns) are still Python `None` on a freshly-constructed row before the first flush, so `0.0 * None` raised `TypeError`, caught by a broad except upstream, silently aborting the *entire* skill-competence batch for that session. This was flagged (but explicitly deferred, not fixed) by an earlier session as a spawned background task — the re-audit independently confirmed it's 100% reproducible (0 rows written across 6 fully-scored test sessions) and this session actually fixed it: coalesce `rec.attempts`/`rec.quiz_score_avg`/`rec.exercise_score_avg` to 0/0.0 instead of trusting the pre-flush value. **Verified live** with a direct before/after call on a brand-new skill, including the running-average math on a second call.

**4. [Fixed] Follow-up chaining could burn 50-60% of a session's question budget on one topic.** `get_next_question()`'s `already_probed` check counted `SessionResponse` rows sharing `question_id` — but a follow-up's own response always has `question_id = NULL` (it isn't a `question_banks` row), so that count could never exceed 1 once the chain left the original question, and nothing capped further follow-ups. Reproduced in 5/5 test sessions (3 consecutive follow-ups on question 1 was the observed pattern). Fixed with a new `is_followup` boolean column on `SessionResponse`, set by the frontend on submit (`InterviewRoomPage.tsx` now tracks `currentIsFollowUp`/`currentQuestionType` — the latter persisting *across* a follow-up, via a ref, since a follow-up has no type of its own — so panelist-inheritance also doesn't break on a follow-up-of-a-follow-up, a related seam the code-review agent separately found). `already_probed` is now simply `bool(resp.is_followup)`. **Verified live via direct API sequence**: answered a question weakly → got a follow-up → answered that with `is_followup: true` → confirmed `get_next_question` moved to `next_question` instead of chaining a third time, and confirmed the DB row actually persisted `is_followup = true`.

**5. [Fixed] `system_design` questions were silently relabeled "behavioral" and misrouted to the wrong panelist.** Both interview-generation prompts explicitly ask for a `system_design` question_type (the blueprint prompt's `question_breakdown` schema and the per-question schema both list it), and blueprints for senior/technical roles routinely plan one — but `question_banks.ck_question_type` never allowed it, so `_generate_dynamic_questions()`'s normalization step silently downgraded it to `"behavioral"` before persisting, which also meant `panelist_for_question_type` never got a chance to route it to Arjun Mehta (Technical Lead) — every system-design question went to Priya Nair (Hiring Manager) instead, contradicting the panel intro's own claim. Fixed: added `system_design` to the constraint + normalization tuple. **Verified live**: 3 fresh Senior Backend Developer sessions → `system_design` questions now persist with that exact type and correctly route to Technical Lead (checked via `group by question_type, panelist_role`).

**6. [Fixed, low severity] Cross-user question leakage in `get_session()`'s fallback padding query.** The "pad out remaining questions" fallback (used when an active session's question list needs topping up) queried *any* `QuestionBank` row with no career track and not-yet-answered-in-this-session — with no check that the row belonged to this session at all, which could surface a different candidate's AI-generated (possibly resume-personalized, post-Phase-4) questions. Pre-existing, not introduced this session, but flagged as something Phase 4 personalization made worse. Fixed by scoping to `session.blueprint["_question_ids"]`, same as `get_next_question()` already correctly does, falling back to the old heuristic only for sessions predating that field.

**7. [Fixed, low severity] Integrity-note check excluded the single most suspicious input.** `_integrity_notes()`'s guard was `0 < secs < (words / 2.5)` — the `0 <` clause meant a genuine 0-second submission on a 40+ word answer (the most implausible case this check exists to catch) was never flagged, while 1 second was. Removed the exclusion.

**Claims independently verified as actually true** (the adversarial reviewers checked these themselves rather than trusting the doc): the two `SessionFeedbackResponse` construction sites really are in sync; multi-judge scores are genuinely independent (32 real rows checked, zero identical triples); `verify_evidence_quote` really does a substring check; `ReviewableSessionOut` really withholds the AI score from blind reviewers; all 4 admin calibration endpoints are properly `require_admin`-gated with clean validation on every edge case tried (bad scores, invalid enums, wrong owner, double-submit); novel-role competency generation is consistently good, including on deliberately nonsensical titles; the migration `downgrade()` paths are correctly ordered.

**Standing caveat, not fixed (needs an environment change, not code):** `ANTHROPIC_API_KEY` is empty in this dev container, so there is currently no live LLM fallback at all — the readiness-report reliability fix (item 1) closed the JSON-truncation failure mode, but a Groq quota exhaustion (as opposed to a brief per-minute throttle) will still degrade to the honest fallback report until the quota window resets or a real second-provider key is configured. This session's own heavy testing volume (two full audit agents doing live QA, plus this fix-verification round) was enough to exhaust it near the end — don't mistake that for an ongoing app defect if you see it happen again shortly after a testing burst.
